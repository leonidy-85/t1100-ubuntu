# IT6112: вендорская инициализация (RE, 03.11.2026)

Источник — **вендорские бинари с платы**, не догадки:

| Бинарь | Что в нём | Где нашли |
|---|---|---|
| `boot_a_5.1.6.110.img` → `kernel` (gzip, arm64 `Image` 4.14.186) | драйвер моста `it6112` (вкомпилирован, kallsyms на месте) | `scripts/bootimg_extract.py` + `vmlinux-to-elf` |
| `bin/.../lk-verified.img` (Thumb-2, 32-bit LK) | **полная** инициализация моста + конфиг-структура `tv110xum_lb2` | дизассемблер, см. ниже |

> Важно: **в ядре 4.14 мост только «переинициализируется»** (`it6112_mipi_tx_init`
> пишет 9 регистров и не трогает PLL). Всю настоящую настройку делает **LK**,
> поэтому RE ядра недостаточно — понадобился LK.

## 1. Один вход DSI или два? — **один вход, два выхода**

| Факт | Значение |
|---|---|
| RX-блок в LK/ядре | **один**, I2C `0x5e` (второго адреса/клиента нет) |
| TX-блок | `0x56`, регистр `0x11` бит3 = `cfg[3]` = **0** ⇒ **8 lane** на выходе |
| Разбиение панели | вендорский `lcm_get_params` отдаёт `hdisplay = 1600` и `800` (половина) — панель двухканальная, по 800 px на канал |
| Вход | 4 lane, `1534.8 Мбит/с` (наш замер), `0x5e 0x21` bit3 = автоопределение формата сработало |

Итого: IT6112 на этой плате — **single-input DSI (4 lane) → dual output DSI
(2 × 4 lane)**. **DSI1 не нужен**, отсутствие `dsi1` в mainline не блокер.
Наличие `dsi1@1401f000` в стоковом DT — свойство платформы MT6771, не этой панели.

`lk-verified.img`, file offset **`0x90ea8`** (тот же тип структуры лежит в ядре
по `0xffffff80099b2490` — это **не** «конфиг PLL», а per-panel cfg; первые 9
байт `01 00 00 00 3e 01 00 04 03` совпадают с тем, что пишет
`lcm_init` ядра 4.14):

| Поле | Значение | Куда идёт |
|---|---|---|

| `cfg[0x06]` | 0 | `0x10` bit1 (inverse MCLK) |
| `cfg[0x09]` | 1 | «расширенный» блок; регистр **`0x46` не используется** |
| `cfg[0x0a]` | 1 | `0x44` bit2 |
| `cfg[0x0b]` | 1 | пересчитывать `0x22`/`0x1f` из измеренного MCLK |
| `cfg[0x0c]` | 1 | `0x21` bit1 |
| `cfg[0x14]` | 0 | `0xd0` (PLL ref divider) |
| `cfg[0x18]` | 0 | `0x25` + low nibble `0x26` (делитель M) |
| `cfg[0x1c]` | 0 | `0x23` + low nibble `0x24` (делитель N) |
| `cfg[0x20]` | 3 | low nibble `0x3c` |
| `cfg[0x21]` | 0x40 | `0x22` (статический фолбэк) |
| `cfg[0x22]` | 0x80 | `0x1f` (статический фолбэк) |
| `cfg[0x23]` | 1 | `0x11` bit4 = 0 |
| `cfg[0x24]` | 4 | low nibble `0x45` |
| `cfg[0x55]` | 0 | ветка `0x78`/`0xd3` **не выполняется** |
| `cfg[0x61]` | 20 | в формуле ниже |

## 3. TX-блок: что реально пишет LK (код `0x1ed9c..0x1eeb8`)

```
0x05 bit0 = 1            (не bit1 — «SW_RST» в WIP-драйвере прочитан неверно)
0x05 bit5 = 1            HOLD_TX
0xd0 = (cfg[0x14] << 2) & 0xfc = 0x00
delay 2 ms
0x21 bit1 = 1
0x23 = 0x00               \
0x24 low nibble = 0x00     / делитель N = 0 → автоматический режим
0x25 = 0x00               \
0x26 low nibble = 0x00     / делитель M = 0
0x3c low nibble = 3
0x10 bit5 = 1
0x22 = cfg[0x21]          (затем перезаписывается формулой)
-- расширенный блок (cfg[9] = 1) --
0x11 bit4 = 0
0x10 bit1 = 0
0x11 bit3 = 0             ⇒ 8 lane
0x3c bit5 = 1
0x44 bit2 = 1
0x45 low nibble = 4
0x47 high nibble = 0x10
0xb0 = 0x27
0x1f = cfg[0x22]          (затем перезаписывается формулой)
delay 2 ms
```

## 4. Формула для `0x22` / `0x1f` (код `0x1eef6..0x1ef8c`)

Выполняется, когда `cfg[0x0b] = 1` (наш случай), **после** измерения RCLK/MCLK
через `0x5e 0x94..0x9b` и **до** DCS-команд:

```
q     = 1e9 / mclk_khz                  (целочисленно)
r8    = (6*q - K) / q                   (K = 20000)
reg1f = r8 ? r8 + 9 : 3
reg22 = ((K*8 - 3*q) / (2*q)) + 20      (вариант 8-lane; 4-lane: K*8-3q/2 → 1.5q/q)
K     = 125 * (cfg[0x24] + 4) * cfg[0x61] = 125 * 8 * 20 = 20000
```

Для MCLK 193…199 МГц (что и меряет наша плата): `q ≈ 5025..5181` ⇒
**`0x22 = 0x21..0x22`**, **`0x1f = 0x0b`**.

## 5. Ответ на «PLL не запрограммирован»

`0x23 = 0x25 = 0x27 = 0`, `0x3d = 0x3e = 0`, `0xd0 = 0` — **так и должно быть**:
делители в рабочей вендорской конфигурации тоже нулевые (мост сам считает
частоту из принятого потока, `0x5e 0x21` bit3 = auto detect).
`0x46` пишется только при `cfg[9] = 0` (у нас 1), `0xd3` — только при
`cfg[0x55] = 2` (у нас 0). Так что `0xd3 = 0xff` — норма.

## 6. Отличия нашего драйвера (0028) от вендора → патч 0029

| Регистр | Вендор (LK) | было у нас (0028) | стало (0029) |
|---|---|---|---|
| `0x24` low nibble | 0 (старший ниббл делителя N) | **1** (писали V_LPS — портили делитель) | 0 |
| `0x45` low nibble | 4 | **3** | 4 |
| `0x26` low nibble | 0 | не писали (чип: 1) | 0 |
| `0x22` | формула ⇒ ~0x21..0x22 | не писали (чип: 0x30) | формула |
| `0x1f` | формула ⇒ 0x0b | не писали (чип: 0x0b) | формула |
| `0xd0`, `0x21`, `0x23`, `0x25`, `0x3c`, `0x46`, `0x27`, `0xd3` | см. таблицы выше | — | как у вендора |
| `0x05` | bit0, bit5 | bit1, bit5 | bit0, bit5 |
| порядок | RX init → замер MCLK → TX блок → DCS | замер уже после init | RX init → замер → `0x22`/`0x1f` → DCS |

Патч: `patches/0029-drm-panel-it6112-program-the-TX-PLL-timing-block-lik.patch`
(коммит `715ccc62d` в `../linux-t1100`).

## 7. Что осталось непроверенным

- Значения `0x22`/`0x1f` выводятся из **нашего** измерения MCLK; при прогоне
  сверить, что `MCLK` печатается и что `0x22` реально стал `0x21..0x22`.
- Если картинки не будет и после этого — следующий подозреваемый не мост, а
  путь данных OVL→RDMA→DSI (чёрный кадр при живом тайминге). Тайминги панели
  и порядок питания к этому моменту сняты из LK — см. §8.

## 8. Тайминги, питание и статус панели (RE от 03.11.2026, до и после 0029)

После 0029 формула TX-PLL легла (`0x22=0x22`, `0x45=0x24`), но экран чёрный,
поэтому снята вторая порция из того же LK. Загрузочный адрес LK — `0x56000000`
(подтверждено таблицей символов по file offset `0x270`: `0x56000000`,
`0x560a7b00`), т.е. `file offset = addr - 0x56000000`.

Найденные функции (addr = 0x56000000 + file offset):

| Функция | Адрес | Как нашли |
|---|---|---|
| `lcm_get_params` (2 копии, tv110xum_lb2 / hx83102e — значения идентичны) | `0x56031094`, `0x56031b90` | `mov.w r7,#0x640` + `mov.w r6,#0x880` (1600×2176) |
| дамп LCM-параметров (`disp_lcm.c`, печатает `vact/vbp/vfp/...`) | `0x56016da4` | формат `"[DISPCHECK][LCM] vact: %d, ..."` @ `0x630fc` |
| `it611x_power_ldo_on` | `0x5601f0a0` | `%s` = `it611x_power_ldo_on` @ `0x76066` |
| `it611x_power_ldo_off` | `0x5601f0f8` | там же |
| `init_power` панели (все пины в idle → 30 ms → EXT_PWR → 200 ms → DVDD) | `0x560318e8` | вызовы gpio-сеттеров |
| `lcm init` панели (сброс → регистры моста → DCS) | `0x56031a40` | там же, `rst`/`stby`/`ts_rst` |
| gpio-сеттеры `avdd/dvdd/vghl/stby/rst/bl/ts_*/ext_pwr` | `0x5601d1a4..0x5601d330` | таблица имён @ `0x90c18` (stride `0x28`: `name[0x20]`, `gpio`, `active`) |
| `it6112 find chip` (I2C) | `~0x5601e7c0` | `cmp #0x49`/`#0x54` (`'I','T'`), `cmp #0x12`/`#0x13` |
| `disp_lcm_init` (читает DCS `0x0A`, печатает `lcm is connected`) | `0x56017354` | строки @ `0x634e8`/`0x63508` |

### 8.1 Тайминги режима: LK против нашего драйвера

LK печатает их сам (формат `disp_lcm.c`: `vact, vbp, vfp, vact_line, hact,
hbp, hfp, hblank, hactive`), значения — из `lcm_get_params`:

| Поле | В LK (вендор) | У нас (0029) | Расхождение |
|---|---|---|---|
| `hactive` (width) | 1600 | 1600 | — |
| `vact_line` (height) | 2176 | 2176 | — |
| `hact` → hsa | **14** | 109 | ✗ 95 px |
| `hbp` | **44** | 34 | ✗ 10 px |
| `hfp` | **44** | 10 | ✗ 34 px |
| `hblank` | 0 | 0 | — |
| `vact` → vsa | **8** | 220 | ✗ 212 стр. |
| `vbp` | 28 | 28 | — |
| `vfp` | **220** | 8 | ✗ 212 стр. |
| htotal × vtotal | 1702 × 2432 | 1753 × 2432 | ✗ |
| pixel clock | 248 356 кГц (60.00 fps, см. ниже) | 255 797 кГц | ✗ 7 441 кГц |
| число lane | 4 (`params[0x180] = 4`) | 4 | — |
| формат | RGB888 (`dsi.mode=1`) | RGB888 | — |
| режим DSI | `SYNC_PULSE_VDO_MODE` (`params[0x16c] = 1`) | `VIDEO\|VIDEO_SYNC_PULSE` | — |
| физический размер | 166 × 226 мм (`params[0x3d0/0x3d4]`) | 166 × 226 | — |

Вывод: **расхождения есть и они существенные** — в v синхроимпульс и передний
porch поменяны местами (220/8 ↔ 8/220), h-тайминги неверны целиком. Набор
`28/220/44/44` совпадает с тем, что отдаёт стоковое ядро 4.14 (dmesg:
`lcm_get_params ... PLL_CLOCK = 790`), т.е. это не артефакт LK.

Про `PLL_CLOCK = 790`: LK берёт его из DT-свойства `LCM.pll_clock` (читается
`0x5601d748/0x5601d81c`, пишется в `params[0x224]`, печатается как
`params->dsi.PLL_CLOCK`). Единицы в этой ветке — «elink»-овские (790 ≈
DDR-частота линии, т.е. ~1580 Мбит/с на lane), тогда как mainline считает
частоту линии из pixel clock и bpp. Пока в драйвере выставляется pixel clock
под 60.00 fps (`videolfb-fps = 0x1770 = 6000` в `/chosen`, т.е. 60.00 Гц) при
вендорских porch'ах: `1702 × 2432 × 60 = 248 355 840` → **248 356 кГц**
(линия 1.490 Гбит/с на lane ≈ 745 МГц DDR против 790 у вендора, −5.7 %). Если
после 0030 мост не залочится, следующий шаг — задавать частоту линии явно, а
не через pixel clock.

### 8.2 Порядок включения питания и пинов

LK, `it611x_power_ldo_on` (`0x5601f0a0`) + `init_power` панели (`0x560318e8`)
+ `lcm init` (`0x56031a40`):

```
rst=0, stby=0, bl=0, dvdd=0, ext_pwr=0, ts_avdd=0, ts_rst=0
delay 30 ms
ext_pwr = 1
delay 200 ms
dvdd = 1
delay 2 ms
ts_rst = 1
delay 5 ms
rst = 1; 5 ms;  rst = 0; 20 ms;  rst = 1; 165 ms     ← сброс моста
init регистров моста (RX → замер MCLK → TX), затем DCS
```

| Шаг | В LK | У нас (0027/0029) | Расхождение |
|---|---|---|---|
| порядок рельсов | `ext_pwr` → 200 ms → `dvdd` (+DSV) | все рельсы сразу, затем `ext_pwr` | ✗ |
| пауза после `ext_pwr` | 200 ms | 20 ms | ✗ |
| пауза после `dvdd` | 2 ms | — | ✗ |
| `stby` | **0** (никогда не поднимается) | **1** | ✗ |
| `rst` | 1 (5 ms) → 0 (20 ms) → 1, затем **165 ms** до первого I2C | 1 (12 ms) → 0 (12 ms) → 1 (12 ms) → сразу I2C | ✗ |
| `ts_rst` (тач) | 1 после рельсов | не трогаем | ок для дисплея |
| выключение | `dvdd`=0 → 23 ms → `ext_pwr`=0 | рельсы off, `ext_pwr` не трогаем | ✗ |

`stby` — самый спорный пункт: патч 0027 поднял его по логу ядра
(`config gpio stby-gpios output, active = 1`), но это только описание пина, а
LK в рабочей последовательности пишет в него 0 и больше не трогает. Если
`STBY` — вход «standby» активного уровня, то 1 = standby: мост продолжает
отвечать по I2C, но TX может быть выключен (ровно наша картина). 0030 приводит
в соответствие с LK; если это регрессия — откат в одну строку.

### 8.3 Как вендор проверял, что панель жива

1. **Мост**: I2C `0x56`, читаются регистры `0x00`/`0x01`, ожидается `'I'`
   (`0x49`) и `'T'` (`0x54`); ревизия (`0x02`) `0x12` → it6112, `0x13` →
   it6113 (кладётся в `cfg[0x54]`/`cfg[0x55]`, печать `find %s, rev: 0x%02x`,
   иначе `can not find chip`).
2. **Панель**: `disp_lcm.c` после `lcm init` делает DCS-read регистра
   **`0x0A`** (`get_power_mode`), печатает `[DISP]read from lcm 0x0A: %d` и
   `[DISP]lcm is connected`. Ожидаемое значение в коде не сравнивается —
   важно, что чтение вернулось. Наш драйвер такого чтения не делает вовсе;
   как дешёвый индикатор «панель отвечает» его стоит добавить (отдельный шаг,
   не в 0030).

### 8.4 Per-panel байт-конфиг целиком (`0x90ea8`)

Первые 9 байт `01 00 00 00 3e 01 00 04 03` совпадают с тем, что пишет
`lcm_init` стокового ядра; дальше — `cfg[]`:

| idx | значение | куда идёт / смысл (по коду) |
|---|---|---|
| `cfg[0]` | 1 | флаг инициализации/валидности (в LK не читается в этой функции) |
| `cfg[1]` | 0 | RX `0x0c`: биты 3..7 (`cfg[1] << 3`) |
| `cfg[2]` | 0 | RX `0x0c`: биты 2..7 (`cfg[2] << 2`) |
| `cfg[3]` | 0 | TX `0x11` bit3: 0 = 8-lane выход; RX `0x80` bits0..5: 7 (иначе 3) |
| `cfg[4]` | 0x3e | RX `0x27` = 62 (задержка/таймаут HS?) |
| `cfg[5]` | 1 | RX `0x11` bit1 (inverse MCLK) |
| `cfg[6]` | 0 | TX `0x10` bit1 (inverse MCLK) |
| `cfg[7]` | 4 | в этой функции не используется |
| `cfg[8]` | 3 | не используется здесь |
| `cfg[9]` | 1 | «расширенный» блок; при 1 регистр `0x46` не пишется |
| `cfg[0xa]` | 1 | TX `0x44` bit2 (PRE_1T) |
| `cfg[0xb]` | 1 | пересчитывать `0x22`/`0x1f` из измеренного MCLK |
| `cfg[0xc]` | 1 | TX `0x21` bit1 |
| `cfg[0xd]` | 1 | не используется здесь |
| `cfg[0x10]` | 3 | не используется здесь |
| `cfg[0x11]` | 1 | не используется здесь |
| `cfg[0x14]` | 0 | TX `0xd0` = `cfg[0x14] << 2` |
| `cfg[0x18]` | 0 | TX `0x25` + low nibble `0x26` (делитель M) |
| `cfg[0x19]`, `cfg[0x1d]` | 1 | не используются здесь |
| `cfg[0x1c]` | 0 | TX `0x23` + low nibble `0x24` (делитель N) |
| `cfg[0x20]` | 3 | TX `0x3c` low nibble |
| `cfg[0x21]` | 0x40 | TX `0x22`, перезаписывается формулой (0029) |
| `cfg[0x22]` | 0x80 | TX `0x1f`, перезаписывается формулой (0029) |
| `cfg[0x23]` | 1 | TX `0x11` bit4 = 0 |
| `cfg[0x24]` | 4 | TX `0x45` low nibble (и в формуле `K`) |
| `cfg[0x25]` | 0x0e | не используется здесь |
| `cfg[0x26]` | 0x0f | не используется здесь |
| `cfg[0x27]` | 0xff | не используется здесь |
| `cfg[0x55]` | 0 | ветка `0x78`/`0xd3` не выполняется |
| `cfg[0x5c]` | 0 (u32) | runtime: измеренный MCLK в кГц (пишется RX-замером) |
| `cfg[0x60]` | 0x16 | не используется здесь |
| `cfg[0x61]` | 20 | в формуле `K = 125 * (cfg[0x24]+4) * cfg[0x61]` |

### 8.5 Патч 0030

`patches/0030-drm-panel-it6112-take-the-mode-timings-and-power-seq.patch`
(коммит `cc74a5bfd` в `../linux-t1100`):

- тайминги → `1600×2176`, hsa 14, hbp/hfp 44/44, vsa 8, vbp 28, vfp 220,
  clock 248 356 кГц;
- питание: `ext_pwr` → 200 ms → `dvdd`/DSV → 2 ms, `stby` в 0;
- сброс: 1 (5 ms) → 0 (20 ms) → 1, затем 165 ms до первого I2C;
- выключение: рельсы → 23 ms → `ext_pwr` = 0.

Если и это не даст картинки — дальше путь данных OVL→RDMA→DSI (дампы регистров
SoC через `CONFIG_DEVMEM`): тайминги панели и порядок питания к этому моменту
будут ровно вендорскими.
