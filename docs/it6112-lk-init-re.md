# IT6112: разбор инициализации в LK и правки нормального пути (07.11.2026)

Источник — дамп LK с платы: `build/lk/lk_a.bin` (`mmcblk0p28`, 8 МиБ, sha256
`cedbe12e3fde96c301b776030f251c80c439b566b875a4cb0d063c3cc1b0f76a`). LK грузится
по `0x56000000`, поэтому `file offset = адрес − 0x56000000`; дизассемблирование —
`python3 -c` + capstone (Thumb-2), `objdump` на этом хосте ARM не умеет.

Повод: после эксперимента A (`docs/it6112-experiment-a.md`) панель работает на
состоянии, которое оставил LK, но чёрная с нашей инициализацией. Разбор LK
показал четыре расхождения и одну грубую ошибку порядка.

## 1. Что LK реально делает с мостом

| Адрес | Что |
|---|---|
| `0x560313f0` | RX init (9/0a/0b/05/0c/11/18/19/20/21/44/27/72/8a/a0/80) |
| `0x5601ed9c` | TX init: `0x05=0xfe`, `0x05=0x00`, бит0, HOLD (бит5), PLL, тайминги |
| `0x5601eef6` | пересчёт `0x22`/`0x1f` из измеренного MCLK и **повторный** проход TX init |
| `0x5601f140` | «TX on»: `0x05=0xfe`, `set_bits(0x06,0x04,0x04)`, `0x05=0x00` |
| `0x56031714` | отправитель DCS: собирает пакет из таблицы и пишет в `0x73/0x74/0x75` |
| `0x560318a0` | **power-off** панели: `0x06 bit1=0`, `0x05 bits0..3=0`, `0x05 bits2,3,6,7=0` |

Ключевое: отправитель DCS (`0x56031714`) в самом начале читает `TX 0x05` и
**ничего не отправляет, пока взведён `HOLD_TX` (bit5)**:

```
5603178a: movs r0, #5 ; bl 0x560311a8     ; read reg 5
56031792: ubfx r6, r0, #5, #1
56031796: cbnz r6, <skip the whole send>
```

Наш драйвер (как и WIP 6.16) снимал `HOLD_TX` **после** DCS, значит `exit sleep`
и `display on` в мост не доходили — панель оставалась спать. Это и есть причина
чёрного экрана при живом потоке: SoC гонит кадры, мост их видит (`RX 0x21` bit3),
а панель не разбужена. В эксперименте A `HOLD_TX` не взводился вовсе, поэтому
DCS доходил (и панель была уже разбужена LK).

## 2. Значения четырёх регистров по LK (а не по догадке)

| Регистр | Что делает LK | Было у нас | Стало |
|---|---|---|---|
| TX `0x24` биты 3..0 | `set_bits(0x24, 0x0f, (u32@cfg+0x1c) >> 8 & 0xf)`, `u32@cfg+0x1c = 0x100` ⇒ **1** | `0` | `1` |
| TX `0x26` биты 3..0 | то же из `u32@cfg+0x18 = 0x100` ⇒ **1** | `0` | `1` |
| RX `0x11` | `set_bits(0x11, 0x01, cfg[5])`, `cfg[5] = 1` ⇒ **бит0** | `0x02` (бит1, «inverse MCLK» из WIP) | `0x01` (бит0) |
| TX `0x22` | статически `cfg[0x21] = 0x40`, затем формула (ниже) | формула с K = 20000 ⇒ `0x21` | формула с K2 = 38125 ⇒ `0x2f` при 188 МГц |

### Формула `0x22`/`0x1f` (LK `0x5601eef6`)

```
q     = 1e9 / mclk_khz
0x1f  = ((6q - 20000) / q) + 9            (или 3, если 6q < 20000)
0x22  = ((K2*8 - 3q) / (2q)) + 20         (8-lane; для 4-lane делитель 2q -> q)
```

`K2` считается так (это и было ошибкой первого порта — потерялось слагаемое):

```
5601ef34: ldrb  r3, [cfg+0x61]   ; 20
5601ef38: ldrb  r4, [cfg+0x24]   ; 4
5601ef3c: adds  r4, #4           ; 8
5601ef3e: mul   r4, r3, r4       ; 160
5601ef42: adds  r4, #0x91        ; 305
5601ef44..4a: r4 *= 125          ; 38125
```

Проверка: при частоте LK (~197 МГц, 1580 Мбит/с) формула даёт `0x30` — ровно то,
что читается в рабочем состоянии моста (`refs/device/it6112-regs-expA2.txt.gz`),
а при нашей (188 МГц, 1490 Мбит/с) — `0x2f`. Прежний K = 20000 давал `0x21`,
то есть ошибку ~30 % в этом тайминговом регистре.

## 3. Штатная последовательность DCS у LK

Найдена таблица (stride `0x24`, поля: `[4]` → `0x75`, `[5]` → длина, `[6..]` →
байты в `0x73`, ECC считается и кладётся в `[9]`):

```
e00: 0x75=0x87 len=8 : 05 11 00 36 | 05 29 00 1c   ; exit sleep + display on
e01: 0x75=0x87 len=4 : 05 10 00 2c                 ; enter sleep
e02: 0x75=0x87 len=4 : 05 28 00 06                 ; display off
e03: 0x75=0x87 len=4 : 05 11 00 36                 ; exit sleep
e04: 0x75=0x87 len=4 : 05 29 00 1c                 ; display on
e05: 0x75=0x87 len=3 : 50 5a 09                    ; brightness 0x5a = 0x09
```

То есть наш пакет (`0x73 = 05, cmd, 00, ecc`, `0x74 = 0x44`, `0x75 = 0x87`)
побайтово совпадает с LK — сам формат был верен, не хватало только снятия
`HOLD_TX` перед отправкой.

## 4. Прогоны на железе (07.11)

| Образ | Что в нём | Экран | sha256 |
|---|---|---|---|
| `boot_ubuntu20` | наш init + `keep=all` (без четырёх регистров), без снятия HOLD | **чёрный**, подсветка есть | `46ae92d7…2f93` |
| `boot_ubuntu21` | HOLD снимается **до** DCS, `0x24/0x26 = 1`, RX `0x11` бит0, K2 = 38125 (`0x22 = 0x2f`), `0x06 |= 0x04` как в LK «TX on» | **чёрный**, подсветка есть | `691a3312…634d` |

Регистры после `boot_ubuntu21` (`post-dcs`, полный дамп в этом образе):

```
tx 00-2c: 54 49 12 61 b0 00 04 00 00 00 00 00 00 08 18 04 a0 63 00 24 ff ff ff ff
          00 00 ff ff ff ff ff 0b 24 03 2f 00 01 00 01 00 00 00 40 00 00
```

Против рабочего состояния LK остались два отличия в этом диапазоне:

* `TX 0x06` = `0x04` (наш `0x06 |= 0x04` из «TX on») против `0x00` у LK;
* `TX 0x22` = `0x2f` (наша частота) против `0x30` (частота LK) — ожидаемо;
* `TX 0x0d..0x0f` — живые счётчики, меняются сами.

## 5. Что дальше (первый шаг после возврата платы)

1. Снять **полный** дамп регистров (`0x00..0x6f`, `0x78..0xff` — уже включён в
   `it6112_dump()`) в двух прогонах: `skip_init=1` (состояние LK) и нормальный
   init, и сравнить карты целиком: прежние дампы покрывали только `0x00..0x2c`,
   `0x44..0x47`, `0xb0`, поэтому отличия вне этого диапазона не проверены.
2. Проверить живьём на рабочем (`skip_init=1`) состоянии одной записью
   `i2cpeek -w 3 0x56 0x06 0x04` (поставить `0x06` bit2) — если картинка
   пропадёт, виноват именно этот бит, и его надо убрать из нашей «TX on».
3. Если `0x06` не при чём — сверить полный дифф и убрать из init всё, чего нет у
   LK (кандидаты: `0x3c` bit5, `0x45`, `0x47`, `0xb0`, запись `0x11` bit3/bit4).
4. Отдельно проверить гипотезу «мост не переживает наш power-cycle/reset в
   `probe`»: маска, при которой `probe` не трогает рельсы и reset (как в
   эксперименте A), но `prepare()` выполняет полный init.

## 6. Патч 0037

`patches/0037-drm-panel-it6112-…patch`, коммит в `../linux-t1100`:

* переключатель `t1100.it6112_keep=<list|all|mask>` (пропуск записи отдельных
  регистров, только через cmdline, без пересборки);
* убран вызов «mipi_power_on» — это power-off хелпер LK (`0x560318a0`);
* в начале TX init — импульс `0x05 = 0xfe`, `0x05 = 0x00` как у LK;
* `HOLD_TX` снимается **до** DCS: `0x05=0xfe`, `set_bits(0x06,0x04,0x04)`,
  `0x05=0x00`;
* `0x24`/`0x26` = 1, RX `0x11` бит0, K2 = 38125 в формуле `0x22`;
* полный дамп регистров моста в лог (диагностика).

**Статус:** на железе образ с этими правками (`boot_ubuntu21`) даёт **чёрный
экран с подсветкой**; правки необходимы, но недостаточны. Итог эксперимента A
(`skip_init=1`) не затронут — он по-прежнему даёт картинку.
