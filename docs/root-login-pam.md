# Вход root: PAM-запреты и почему они возвращаются

Документ про грабли, которые на этом порте повторялись уже несколько раз:
**root не может войти в графику (или в консоль), хотя пароль верный**. Причина
всегда одна и та же — правило upstream `user != root` в PAM-службе, которое
срабатывает **до** проверки пароля. Разные сессии чинили разные службы, и
проблема возвращалась на новом месте.

## 1. Симптомы

| Где | Что видно |
|---|---|
| Экран блокировки KDE | пароль верный, «не пускает»; в journal — `requirement "user != root" not met by user "root"` |
| Экран входа SDDM (greeter) | то же самое; автологин при этом работает — то есть «обычно всё нормально», а вручную войти нельзя |
| SSH | `Permission denied (publickey)` при испорченных правах `/root` (смежная грабля, см. §5) |
| Консоль (Ctrl+Alt+F3) | обычно пускает — `login` использует другой PAM-файл, в нём запрета нет |

## 2. Корень

Ubuntu/Debianship-сборки (и KDE-пакеты) кладут в PAM строку:

```
auth required pam_succeed_if.so user != root quiet_success
```

Она означает «root в эту службу не пускать». У нас root — рабочий пользователь
(автологин SDDM, весь десктоп под root), поэтому в **каждой** службе, которой
пользуется вход, эту строку надо снять.

Две ловушки, из-за которых это повторяется:

1. **Два каталога.** Часть служб лежит в vendor-каталоге `/usr/lib/pam.d/`
   (`kde`, `kde-fingerprint`, `kde-smartcard`, `polkit-1`, `systemd-user`), а
   `/etc/pam.d/` перекрывает его. Правка только `/etc/pam.d/<служба>`
   переживает обновление пакета, но при **переразвёртывании пакета** vendor-копия
   снова оказывается свежей; правка только vendor-копии не перекрывает
   `/etc`. Правильно — **оба** места, и оба в `rootfs-overlay/`.
2. **Оверлей может откатить.** `tools/host/deploy-overlay.sh` раскладывает
   `rootfs-overlay/` на плату. Если исправленного файла там нет — на плате
   останется/вернётся upstream-версия.

## 4. Диагностика и починка

Быстро, одной командой:

```sh
tools/host/check-root-login.sh            # только проверка
tools/host/check-root-login.sh --fix      # снять активные запреты (с бэкапом *.bak-<дата>)
```

Скрипт проверяет:

1. активные (не закомментированные) `user != root` в `/etc/pam.d` **и** `/usr/lib/pam.d`;
2. `passwd -S root` (`P` — пароль есть, `L`/`NP` — нет);
3. хеш в `/etc/shadow` (пусто/`!`/`*` — войти по паролю нельзя);
4. настройку автологина SDDM.

Вручную то же самое:

```sh
grep -rnE '^[[:space:]]*(auth|account).*user[[:space:]]*!=[[:space:]]*root' /etc/pam.d /usr/lib/pam.d
passwd -S root
journalctl -b | grep -i 'user != root'
```

Проверка «пароль подходит» без входа в графику:

```sh
pamtester sddm root authenticate      # если pamtester установлен
# либо: su -c true root  (спросит пароль)
```

Сменить пароль (если подозрение на испорченный хеш — было 12.11, когда `sed`
записал в `/etc/shadow` литерал `HASH`):

```sh
printf 'root:0\n' | chpasswd
getent shadow root | cut -c1-12       # ожидаем $y$j9T$
```

## 5. Смежные грабли того же узла (доступ к плате)

- **Оверлей с uid 1000.** `tar -xf` в `/` сохраняет uid репозитория, `/root`
  становится чужим, и `sshd` со `StrictModes=yes` отказывает в ключе
  («bad ownership or modes for directory /root»). Лечение — `deploy-overlay.sh`
  (`--owner=0 --group=0 --numeric-owner` + chown) либо `chown -R root:root /root`
  из recovery.
- **`chpasswd` вместо sed.** Правка `/etc/shadow` регулярками уже один раз
  записала литерал `HASH` — пароль перестал работать. Только `chpasswd`.
- **Сломанный sshd ≠ сломанный пароль.** Симптом `kex_exchange_identification:
  Connection reset by peer` при живом ping — это не PAM и не пароль: sshd
  падает до баннера (битые права/ключи, перезагрузочный цикл). Пароль в такой
  ситуации проверить нельзя, сначала чинится sshd/доступ.

## 6. Чек-лист после любого `deploy-overlay.sh` / обновления пакетов

```sh
tools/host/check-root-login.sh                 # PAM: ни одного активного user != root
ssh root@10.42.66.66 'passwd -S root'          # P → пароль есть
# и один раз руками: разблокировать сессию (Super+L) и войти паролем
```

Если `check-root-login.sh` нашёл запреты — `--fix`, затем **скопировать
исправленные файлы в `rootfs-overlay/`** и закоммитить, иначе следующий деплой
вернёт всё назад.
