# Аппаратное декодирование видео на MT6771: куда идти (и почему не «просто включить»)

Обновлено: 18.11.2026. Состояние: **не работает, путь выбран, но требует
отдельного проекта**. Ниже — факты, собранные из стокового DTB, стоковой
прошивки `scp_a`, mainline 6.12.114 и публичного вендорного дерева.

## 1. Что известно точно

| Факт | Значение | Источник |
|---|---|---|
| Блок VDEC у MT6771 | регистры `0x16020000…0x16028000`, IRQ **GIC_SPI 250** | `refs/stock-mt6771.dts`: `vdec@16020000`, `vdec_pp@16025000`, `hevc_vld@16028000` |
| У MT8183 в mainline | те же адреса и **та же IRQ 250** | `arch/arm64/boot/dts/mediatek/mt8183.dtsi`: `video-codec@16020000` |
| Драйвер mainline | `mediatek,mt8183-vcodec-dec` (drivers/media/platform/mediatek/vcodec) | `mtk_vcodec_dec_drv.c` |
| Что требует драйвер | rproc-фантом `mediatek,scp` **или** `mediatek,vpu`, дальше IPI-команды `AP_IPIMSG_DEC_*` | `mtk_vcodec_dec_drv.c:378-390`, `common/mtk_vcodec_fw_*.c` |
| SCP у MT6771 | `scp@10500000`, SRAM `0x80000`, cfg `0x105c0000…0x105d9080`, IRQ **GIC_SPI 174** | `refs/stock-mt6771.dts` |
| SCP у MT8183 в mainline | `scp@10500000`, SRAM `0x80000`, cfg `0x105c0000`+`0x19080`, IRQ **GIC_SPI 174** | `mt8183.dtsi`, `drivers/remoteproc/mtk_scp.c` |
| mainline `mtk_scp` | поддерживает mt8183/8186/8188/8192/8195, **MT6771 нет** | `mtk_scp_of_match[]` |
| Стоковая `scp_a` (p21, 8 МиБ) | sha256 `a828a4da…f89a283`, заголовок `tinysys-loader-CM4_A`, пути `project/CM4_A/mt6771/…`, IPI **v02** | дамп p21 (`dd`), `strings` |
| Сервис видео в стоковой SCP-прошивке | **отсутствует**: строк `vdec`/`codec`/`h264`/`hevc`/`vp9` — 0 | `strings -n 4 scp_a.img \| grep -ic vdec` → 0 |

Главный вывод по SCP: **сам SCP-блок у MT6771 и MT8183 одинаковый** (адрес,
IRQ, окно cfg, `tinysys` + IPI v02), то есть порт `mtk_scp` реалистичен. Но
видео он не даёт: в стоковой прошивке SCP нет сервиса декодирования, а
mainline-драйвер ждёт именно его.

## 2. Почему это не «включить узел в DTS»

В `mt6771.dtsi` узел `vcodec_dec` был **удалён** с комментарием «нужна
SCP-прошивка» (`/delete-node/ &vcodec_dec;`). Сегодняшняя проверка это
подтверждает: дело не в адресах (они совпадают), а в том, что некому
обслуживать IPI-команды декодера.

Вендорный путь тоже не «в лоб»: в публичном дереве 4.4.146
(`Hadenix/android_kernel_alps-4.4`) для MT6771 есть
`drivers/misc/mediatek/videocodec/mt6771/` (VAL: drv/hal/val) и
`drivers/misc/mediatek/vpu/mt6771/`, но в VAL **нет** ни `request_firmware`,
ни `scp`/`vpu` вызовов — то есть либо часть кода вырезана из публичного
дерева, либо декодер MT6771 управляется регистрами напрямую. Ни того, ни
другого без вендорного исходника не доказать.

## 3. Варианты и их цена

| Вариант | Что нужно | Оценка |
|---|---|---|
| **A. Порт `mtk_scp` под MT6771 + стоковая прошивка SCP** | `mtk_scp_of_data` для MT6771 (по факту = `mt8183_of_data`), memory-region для SRAM, включение `CLK_INFRA_SCPSYS`; затем проверить, что прошивка отвечает на IPI | 1–2 дня на «прошивка жива/не жива». **Декод не даст**: сервиса vdec в fw нет |
| **B. Написать VDEC-драйвер по вендорному VAL** | вендорный исходник (не публичен), карта регистров (`0x16020000…`), формат firmware (если он есть), V4L2 stateful-обвязка | недели, без TRM и без исходника — риск не сойтись |
| **C. Софт-декод (как сейчас)** | ничего: VP9/AV1 на CPU, 4K60 ≈ 170 % CPU на 8×A53 | работает уже сейчас; 720p–1080p комфортно |
| **D. GPU-декод** | Mali-G72 **не имеет** видеоблока (это отдельный IP), Vulkan Video на panfrost нет | невозможно |

**Решение:** пока — C (софт-декод), отдельным треком — спайк A (короткий, с
чётким критерием «SCP отвечает на IPI»), B — только если найдётся вендорный
исходник VDEC для MT6771. Узел `vcodec_dec` в DTS не возвращаем, пока A не
даст IPI-ответ.

## 4. Спайк A: пошагово (следующая сессия)

1. **Прошивка.** Уже снята: `scp_a` = `/dev/mmcblk0p21`, sha256
   `a828a4da761a533e0ad06425abff190b28fca91f6ca2a4758f07f8d2af89a283`.
   ELF-заголовок в начале есть (`0x58881688`, `tinysys-loader-CM4_A`) —
   mainline `scp_elf_load_segments()` ждёт именно ELF32.
2. **DT.** Вернуть узел: `scp@10500000` с `compatible = "mediatek,mt6771-scp"`,
   `reg = <0 0x10500000 0 0x80000>, <0 0x105c0000 0 0x19080>`,
   `reg-names = "sram","cfg"`, `interrupts = <GIC_SPI 174 IRQ_TYPE_LEVEL_HIGH>`,
   `clocks = <&infracfg CLK_INFRA_SCPSYS>`, `memory-region = <&scp_mem_reserved>`
   (регион 1 МиБ в `reserved-memory`, которого сейчас нет).
3. **Драйвер.** `mtk_scp_of_match` += `mediatek,mt6771-scp` с
   `mt8183_of_data`; проверить `ipi_buf_offset` (в MT8183 = `0x7bdb0` — у
   MT6771 может отличаться; берётся из ELF-символа прошивки
   `scp_elf_read_ipi_buf_addr()`).
4. **Критерий успеха спайка:** в dmesg `scp: ready`, `rproc scp: ... started`,
   и `echo test > /sys/class/remoteproc/remoteproc0/...` нет; лучше —
   `scp_ipi` тест-модуль отвечает. Если прошивка стартует — фиксируем факт и
   отдельно решаем про vdec; если нет — A закрывается, остаёмся на C.

## 5. Что это даёт проекту

- Порт SCP — сам по себе шаг вперёд: SCP управляет сенсорами/аудио/камерой в
  вендорной схеме, и без него часть периферии недоступна.
- Аппаратный декод — единственный реальный путь к 4K без 170 % CPU; но он
  требует либо вендорного fw с сервисом vdec, либо собственного драйвера.
- Пользовательский уровень уже готов к hw-декоду: `mpv`/`ffmpeg` умеют
  `--hwdec=v4l2m2m`, Firefox — нет (только VA-API), так что браузер останется
  на софт-декоде в любом случае.
