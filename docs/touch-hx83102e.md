# HX83102E: протокол по стоковому драйверу (reverse engineering)

Документ отвечает на вопросы «что слать, куда читать, как настроить INT» для
in-cell дигитайзера **HX83102E** (панель BOE TV110XUM-LB2, i2c0 0x48, EINT 1,
reset GPIO158, `ts-avdd` GPIO163) — по **дизассемблированному вендорскому
драйверу** из стокового `boot_a` 5.1.6.110.

Важно: это не «источник истины по TRM» (его нет), а реконструкция поведения
вендорского кода. Где вывод неоднозначен, это явно помечено.

---

## 1. Транспорт: как вендор говорит с чипом

`himax_bus_read(u8 sub, u8 *buf, int len)` @0xA9E278 — **один** `i2c_transfer`
из двух сообщений:

1. write 1 байт — это *суб-адрес* (`msg[0].len = 1`, подтверждено
   `stur w9,[sp,#0xa]` с `w9 = 0x10000`);
2. read `len` байт (`msg[1].flags = I2C_M_RD`), `len ≤ 0x100`, иначе `-ENOMEM`.
   Ретраи: 3 попытки, при провале — `"[HXTP][ERROR] %s: i2c_read_block retry over 3"`
   ровно как в стоковом dmesg.

`himax_bus_write(u8 sub, u8 *buf, int len)` @0xA9E400 — то же, `len ≤ 0xFD`.

Пространства адресов различаются **только суб-адресом**:

| суб-адрес | назначение |
|---|---|
| `0x00` | окно AHB: сначала пишутся 4 байта адреса (LE), затем читаются/пишутся данные; используется для `0x1000xxxx` / `0x9000xxxx` |
| `0x0D` | управление burst |
| `0x13` | команда burst |
| `0x11` | 1-байтовая команда «отпустить указатель кадра» (см. §3) |
| `0x30` | **блок отчёта (кадр касаний)**, читается burst’ом напрямую |
| `0x08`, `0x0C`, `0x27`, `0x31`, `0x32`, `0x95` | служебные, встречаются в таблице команд IC |

`hx83102_register_read(u32 *addr, u8 *out)` @0xA99598 (последовательность
inlined в нескольких местах):

```
write(0x13, {0x31}, 1)          // burst on
write(0x0D, {0x10}, 1)          // burst, без auto-add
write(0x00, addr, 4)            // 4-байтный AHB адрес, LE
read (0x00, out, 4)             // 4 байта данных
```

`hx83102_burst_enable(auto_add_4_byte)` @0xA98C70 — это ровно две первые
записи (`0x13=0x31`, `0x0D = 0x10 | auto_add`).

Это **не** то, что делает mainline `himax_hx83112b.c`: там `regmap_raw_read()`
с 32-битным `reg` всегда идёт через суб-адрес `0x00` (AHB). Т.е. mainline
читает `AHB 0x00000030`, а вендор для кадра читает **регистр `0x30` восьмибитного
пространства** — разные физические места (см. §3).

## 2. Инициализация (восстановленная последовательность)

### 2.1. Верхний уровень (`hx_ic_register` → dmesg 1.418…1.539)

```
mtk_tpd: himax reset over            (RESET, 12 мс низкий + 12 мс высокий, GPIO158)
[HXTP] _hx83102_init
```

### 2.2. `_hx83102_init` @0xA98D6C

Порядок (по дизассемблеру; в скобках — строки стока):

1. `himax_int_enable(ts, 0)` — INT выключен (`enable = 0`).
2. `msleep(5)` (`usleep_range(5000,5100)`).
3. `himax_int_enable(ts, 1)`.
4. `usleep_range(50000, 51000)` — 50 мс.
5. `read(0x13, 1)` — проверка bus.
6. **sense_off** (цикл, лог `hx83102_sense_off: cnt = %d, data[0] = 0x%02X!`):

```
for (cnt = 0; cnt < 50; cnt++) {
        write AHB 0x9000005C = 0xA5        // "enter save mode / sense off"
        msleep(20)
        read  AHB 0x900000A8               // статус FW
        if (дата != 0x05) → лог, continue  // 0x05 = "FW reload done"
        read  AHB 0x9000005C
        if (дата == 0x87) break            // подтверждение входа в save mode
}
```

   Сток подтверждает: `cnt = 0, data[0] = 0xA5!`, затем `cnt = 1, data[0] = 0x87!`
   (то есть первый проход вернул 0xA5, второй — 0x87, дальше
   `Check enter_save_mode data[0]=C` — проверка содержимого save-режима).

7. `hx83102_chip_detect` (inlined, лог `hx83102_chip_detect:Read driver IC ID = 83,10,2E`):
   - `read AHB 0x10007F40` → ожидается `0x07EAFBEF` (магия доступа);
   - `read AHB 0x900000D0` → 4 байта `83 10 2E 00` = ICID `0x83102E`.
8. `himax_mcu_in_cmd_struct_init` @0xA92E78 — аллокация 6 буферов
   (0x30, 0x28, 0xD1, 0x70, 0x10, 0x2B) и заполнение таблицы операций
   (см. §5), в т.ч. базовый адрес командного окна `0x20FB6C0/0x20FB6C8`.
9. `himax_mcu_in_cmd_init` @0xA9336C — раскладка «адрес→байт» в буферы:
   `bufA` (0x28 Б, суб-адреса 0x00/0x0C/0x13/0x0D/0x31/0x32/0x00/0x31/0x10/
   0x80020020) и `bufB` (0xD1 Б) с содержимым блока отчёта:
   `bufB[0xC3] = 0x11`, `bufB[0xC4] = 0x00`, `bufB[0xC5] = 0x01`,
   `bufB[0xC6] = 0x30` — именно эти байты потом читает путь кадра (§3).
10. `himax_hx83102e_reg_re_init` @0xA994C8 — переопределения для 83102E:
    - `himax_parse_assign_cmd(0x100072EC, bufB+0x20, 4)`;
    - `bufD[0x18] = 0x30`, `bufD[0x19] = 0x1E`;
    - `bufA[0x0C] = 0x80020004` (4 байта);
    - подмена слотов таблицы операций: `+0x00 → 0xA9A068`,
      `+0x18 → 0xA9A1BC`, `+0xF0 → 0xA9A450`, `+0x210 → 0xA98FC0`.
11. `himax_hx83102e_func_re_init` — второй проход по таблице (без регистровых
    записей, только указатели).

### 2.3. `hx83102e_chip_init` @0xA99AE0

Читает «touch information» и печатает (порядок из dmesg 1.537):

```
IC cell type = 1
HX_RX_NUM = 48, HX_TX_NUM = 32
HX_MAX_PT = 10
HX_Y_RES = 2176, HX_X_RES = 1600
HX_INT_IS_EDGE = 1, HX_STYLUS_FUNC = 0
HX_STYLUS_ID_V2 = 0, HX_STYLUS_RATIO = 1
```

Далее: `himax_ts_register_interrupt` (debounce, request_irq — §4),
`himax_int_enable(0)`, `himax_report_data_init` (§3), `input_register`.

### 2.4. `himax_mcu_power_on_init` (в workqueue, dmesg 1.74…2.00)

```
wait FW reload 1..4 times:
   read 0x10007F40   (= 0x07EAFBEF)
   read 0x900000A8   (ждём 0x05)
   read 0x900000E8   (= 0x04 39 01 08)
   read 0x900000E4   (= 0x02 00 00 00)

→ "FW reload done"
PANEL_VER  = 0x45      (из 0x900000E8/0xE4-области)
FW_VER     = 0x8203
TOUCH_VER  = 4

Cusomer ID = "XY", Project ID = "0623K"

```

### 2.5. Проверка flash/CRC и «не обновлять»

```
hx_chk_flash_sts(131072)               // 128 КиБ
himax_mcu_calculateChecksum(size=131072) → "Waiting for HW ready!" в цикле
himax_get_fw_ver_bin (файл Himax_firmware.bin, CONFIG_TABLE@0x10400,
                      CID_VER@0x11402, FW_VER@0x11405, CFG_VER@0x11500)
→ версии совпали → "Need not update!"
```

### 2.6. Финал

```
himax_int_enable(ts, 1)        // dmesg 2.004: "himax_int_enable: enable = 1"
```

**Итого минимальный «поднять чип» = §2.2 шаги 1–11 + §2.4 wait + §2.6.**
CRC/flash-обновление для работы не нужно (вендор сам в него не заходит, если
версии совпали).

Что именно «включает выдачу кадров» — по коду это **не** отдельная команда, а
совокупность: (а) burst-режим (`0x13=0x31`, `0x0D=0x10`) и (б) выход из
save-режима, т.е. штатный `sense_on` после `sense_off`. Пока чип в save-режиме
(0x87 подтверждён, `0x900000A8 != 5`), он отдаёт константу вместо данных — это
ровно наблюдаемый `0xEC`/`0x00` (см. §3.3).

## 3. Блок отчёта: где лежит кадр

### 3.1. Путь чтения (0xA9C318 → слот `[0x20FB830]` → 0xA95DAC)

```
himax_touch_get(ts, type):
    memset(buf, 0, 0x78)
    len = (type == 3) ? 0x80 : ts-><len>       // 0x80 = 128 байт «с запасом»
    slot[0x20FB830](buf, len)                  // = 0xA95DAC
```

`0xA95DAC`:

```
cmd = [0x20FB6C8]                     // таблица IC (bufB, 0xD1 байт)
himax_bus_write(cmd[0xC3] = 0x11, {cmd[0xC4] = 0x00}, 1)   // 1 байт 0x00 в рег 0x11
himax_bus_read (cmd[0xC6] = 0x30, buf, len)                // burst-чтение с рег 0x30
```

Отсюда: **кадр отдаётся регистром `0x30` 8-битного пространства**, читается
одним burst-чтением, непосредственно перед чтением в регистр `0x11` пишется
`0x00` (в вендорском коде это «отпустить/переустановить указатель кадра»).

### 3.2. Размер и раскладка

`himax_report_data_init` @0xA9AAD8:

```
hx_raw_cnt_max = touch_info / 4
rem            = touch_info % 4
touch_info_size = 4 * (HX_MAX_PT + hx_raw_cnt_max) + (rem ? 8 : 4)
              [ + 0x0C, если включён stylus ]
rawdata_fsz  = touch_info_size / (touch_info_size - 0x0C)
```

При `HX_MAX_PT = 10`, `touch_info = 56`: `56/4 = 14`, `56%4 = 0`,
`hx_raw_cnt_max` в логе = **2**, `4*(10+2)+8 = 56` ✓.
Лог стока: `rawdata_fsz = 25, HX_MAX_PT:10, hx_raw_cnt_max:2`,
`hx_raw_cnt_rmd:2, g_hx_rawdata_size:66, touch_info_size:56`.

Следствия:

* **56 — это ровно тот же размер, что в mainline `struct himax_event`.** По
  размеру формат совпадает, «protocol Type B» (в логе
  `himax_chip_common_init: Use Protocol Type B` — та же строка есть в mainline).
* Кадр = 12 четырёхбайтных записей: 10 записей точек + 2 служебных
  (`hx_raw_cnt_max = 2`), плюс 8 байт (заголовок/хвост). Смещение заголовка
  и семантику нибблов восстановить однозначно не удалось — см. §6.

Валидация в `himax_touch_get` (0xA9C5E4…0xA9C7D0):

* контрольная сумма — **16-битная сумма байт до первого нулевого байта**, а не
  сумма всех 56 байт, как в mainline `himax_verify_checksum()`;
* байты `0xEB`, `0xEC`, `0xED` считаются специальными кодами
  (`0xEB`/`0xEC`/`0xED` — счётчики «exception»), байт с `(b >> 4) == 0xF` —
  маркером (`0xFF`-терминатор);
* при «exception» кадре печатается `TP] EXCEPTION event checked - ALL Zero.`

### 3.3. Почему mainline получает `0xEC`

`himax_read_events()` в mainline делает `regmap_raw_read(reg = 0x30, 56)`.
regmap с 32-битным `reg` и LE-форматом шлёт в суб-адрес `0x00` **4 байта
адреса** `30 00 00 00` и читает 56 байт — то есть обращается к `AHB 0x00000030`.
Вендор в это время читает **регистр `0x30`** (тот же номер, другое пространство,
без 4-байтного префикса). Разные места → `0xEC` (константа «нет данных»,
`56 × 0xEC = 0x33A0` — та самая сумма, которую mainline и отвергал) и `0x00`
в покое.

Дополнительно объяснение «живых» байт в `0x3A…0x3E`: это окно лежит
непосредственно за `0x38` в том же 8-битном блоке, поэтому именно туда
попадают байты отчёта при касании, даже если читать «не тем» способом.

## 4. Прерывание

DTS стока (`refs/device/fdt-live.dts.gz`, `himax_touch@48`):

```
reg = <0x48>;
interrupt-parent = <&pio>;
interrupts = <0x01 0x01 0x01 0x00>;      /* EINT 1, edge */
debounce   = <0x01 0x00>;                /* 1 мс */
```

dmesg: `himax_parse_dt: int : 01`, `himax_touch_irq=19d` (GPIO 413),
`irq enabled at qpio: 19`, `ints[0] = 1, ints[1] = 0`.
`refs/device/interrupts.txt`, строка 9:

```
19: 648 533 594 532 219 156 171 138  mt-eint  1  Edge  himax_touch
```

`himax_ts_register_interrupt` @0xA9E8C8:

```
gpio_set_debounce(gpio, 2)                    /* 2 мс, из dts 1 мс */
irq = gpio_to_irq(gpio)                       /* 19 */
request_threaded_irq(irq, handler, thread,
                     IRQF_ONESHOT | IRQF_TRIGGER_FALLING /* 0x2002 */)
   при неудаче — повтор с IRQF_ONESHOT | IRQF_TRIGGER_LOW /* 0x2008 */
```

`HX_INT_IS_EDGE = 1` (из touch info) → **edge, falling**, активный низкий
уровень не используется. Отдельного «enable-регистра INT» в чипе нет:
`himax_int_enable(ts, en)` @0xA9E5CC управляет только локальной маской
(`enable_irq/disable_irq` + флаг `ts->irq_en`), сам чип прерывание не
маскирует.

**Про тик 1 Гц.** Это та же линия, что и у стока (`mt-eint 1 = himax_touch`,
648 срабатываний за аптайм — то есть и в стоке линия тикает без касаний).
Вендорский ISR на каждом прерывании **безусловно читает кадр** (§3.1) и лишь
потом решает, есть ли точки; «пустые» отчёты он не считает ошибкой. Поэтому
тик — это, скорее всего, штатный периодический отчёт прошивки чипа, а не
постороннее устройство на линии. Отдельно стоит проверить bias pin 1 в
pinctrl: сток настраивает EINT через `mt_eint_register` c pull, у нас pin 1
без bias — при плавающем входе возможны ложные фронты.

## 5. Чего не хватает в mainline (по порядку)

1. **Burst-режим**: `write(0x13, 0x31)`, `write(0x0D, 0x10)` — без него
   автоинкремент адреса при чтении не работает.
2. **sense_off/save-mode**: `AHB 0x9000005C = 0xA5`, `msleep(20)`, поллинг
   `AHB 0x900000A8 == 0x05`, подтверждение `read AHB 0x9000005C == 0x87`
   (до 50 попыток). Без этого шага чип может остаться в состоянии, где отдаёт
   константу.
3. **Проверка ID через магию**: перед чтением ICID писать/читать
   `AHB 0x10007F40` (`0x07EAFBEF`); ICID — `AHB 0x900000D0`.
4. **wait FW reload**: 4 итерации `read 0x10007F40 / 0x900000A8 / 0x900000E8 /
   0x900000E4` + `msleep(10)`, критерий — `0x900000A8 == 0x05`.
   Затем версии: `PANEL_VER/FW_VER/TOUCH_VER/DISPLAY_VER/CID_VER`.
5. **sense_on** (симметрично sense_off) + снятие `reload_disable` — вендор
   делает это перед `himax_int_enable(1)`.
6. **Правильное чтение кадра**: `write(0x11, 0x00, 1)` затем
   `i2c burst read` с **регистра `0x30`** (8-битный суб-адрес, без 4-байтного
   AHB-префикса). Не `regmap_raw_read(0x30, 56)`.
7. **Честная контрольная сумма**: 16-битная сумма байт до первого `0x00`
   (вендор), а не сумма всех 56 байт.
8. **Тайминги**: `msleep(5)` между `int_disable`/`int_enable`, 50 мс после
   включения INT, 20 мс в цикле sense_off, 10 мс в wait-FW-reload.
9. **Мелочи**: INT — `IRQF_TRIGGER_FALLING` (не level); debounce 2 мс;
   длина чтения кадра 0x80 (128) в одном из путей, `touch_info_size = 56` —
   парсится.

Что уже есть в mainline и совпадает: ICID-регистр `0x900000D0`, AHB-механизм
(суб-адрес `0x00` + 4-байтный адрес), размер кадра 56, «protocol type B»,
max 10 точек, 1600×2176, INT edge.

## 6. Что осталось неясным

* **Точная раскладка 56 байт.** Размер и 4-байтные записи подтверждены
  (10 точек + 2 служебных + 8 байт), но порядок полей (ниббл id, порядок
  X/Y, где заголовок, где checksum) из кода однозначно не извлекается:
  разбор (`himax_parse_report_points` @0xA9AEB0, `himax_touch_get` @0xA9C318)
  сильно зашумен отладочными ветками. Гипотеза (средняя уверенность):
  запись = `{id|flags, x[11:4], x[3:0]|y[11:8], y[7:0]}`, как в «type B»;
  первые 8 байт — заголовок (счётчик/флаги/сумма), хвост — терминатор.
* **Полная последовательность `sense_on`.** Начало декодировано
  (`write(0x11,0x00)`, `usleep_range(10000,11000)`, чтение через
  `himax_mcu_register_*`), но хвост завязан на таблицу команд `bufB`,
  которую целиком не разбирали.
* **Что именно значит `0x11 = 0x00`** — «release/reload указателя кадра» по
  смыслу места вызова; в TRM не проверено.
* **Точная длина чтения** (0x80 против 56): вендор в одном пути просит 128
  байт в буфер 0x78, в другом — `ts->len`. Скорее всего читается 128 и
  используется 56.
* **Причина тика 1 Гц** — см. §4: гипотеза «штатный пустой отчёт» +
  отсутствие bias на pin 1; на железе не разделено.

## 7. Минимальный эксперимент для проверки (не требует прошивки железа)

На живой плате, с уже поднятым питанием и сбросом, из userland/драйвера:

1. `write(0x13, 0x31)`, `write(0x0D, 0x10)` — burst on;
2. `write(0x11, 0x00)` — 1 байт;
3. `read(0x30, buf, 56)` — burst-чтение **регистра** 0x30 (i2c read без
   адресного префикса);
4. сравнить с: `read AHB 0x90000030` (то, что делает mainline сейчас) и с
   `read(0x38, ...)`, `read(0x3A, 6)`.

Критерий: в покое кадр должен быть «нулевым» (все точки 0), при касании —
меняющиеся 4-байтные записи с `id` в 0…9. Если шаг 3 даёт то же, что шаг 4
(`0xEC`/`0x00`), значит чип всё ещё в save-режиме → проверить `0x900000A8`
и повторить `sense_off`/`sense_on` из §2.
