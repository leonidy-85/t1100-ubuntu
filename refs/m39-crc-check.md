# M39 — хвостовой CRC в ROMv4-патче нет; вендор для ROMv4 ничего не срезает (13.11)

## 1. Файл `ROMv4_be_patch_1_0_hdr.bin` (229 384 Б): заголовок 48 Б, тело 229 336 Б

`u4CRC[4]` из заголовка (байты 32…47): `0x0000ffff, 0x00005a10, 0x000121a4,
0x0000205c` — это **не** контрольные суммы тела (два значения не влезают в 16
бит, ни одно не совпало ни с одним расчётом; похоже на размеры/адреса секций).

Расчёт сумм по телу без последних N байт и сравнение с этими N байтами:

| N | последние N байт | crc32 | crc16-ccitt | crc16-xmodem | crc16-arc | sum32 | совпало |
|---|---|---|---|---|---|---|---|
| 0 | — | `87c4392b` | `e0fc` | `2408` | `daca` | `010732d4` | нет |
| 2 | `dd9e` | `f36df806` | `1e0c` | `d8c6` | `b839` | `01073159` | нет |
| 4 | `9884dd9e` | `579d1694` | `b5f5` | `2b15` | `a4c6` | `0107303d` | нет |
| 8 | `ec383a6f9884dd9e` | `d4d49f02` | `bd7c` | `93ae` | `85f9` | `01072e70` | нет |
| 16 | `007858f786f4dd2fec383a6f9884dd9e` | `f525eda3` | `a387` | `b58f` | `e6f4` | `01072a23` | нет |
| 32 | `441ffd56…9884dd9e` | `bc2040eb` | `a932` | `101d` | `e73d` | `010724a2` | нет |

⇒ **хвостовой CRC (2/4/8/16 байт) в теле нет**, снимать нечего.

## 2. Вендорская семантика (цитаты)

`common_main/core/wmt_ic_soc.c`, `mtk_wcn_soc_patch_dwn(index)`:

```c
	if (wmt_ic_ops_soc.icId == 0x6765 ||
	    wmt_ic_ops_soc.icId == 0x3967 ||
	    wmt_ic_ops_soc.icId == 0x6761) {
		/* remove patch checksum:
		 * |<-patch checksum: 2Bytes->|<-patch body: X Bytes (X=patchSize)--->|
		 */
		pPatchBuf += BCNT_PATCH_BUF_CHECKSUM;
		patchSize -= BCNT_PATCH_BUF_CHECKSUM;
	}
```

Срез `BCNT_PATCH_BUF_CHECKSUM` применяется **только** к `0x6765/0x3967/0x6761`.
Для `0x0788` (наш) ветки нет — то есть вендор для ROMv4 ничего не срезает, и мы
делаем то же.

`u4CRC[4]` в коде ядра не читается вовсе (`grep -c u4CRC` по `wmt_ic_soc.c` = 0 в
пути загрузки), `u4PatchType` тоже (см. M33).

## 3. Следствие

Гипотеза M38 закрыта: тело мы отправляем байт-в-байт так, как это делал бы
вендор. Значит «229 ack → молчание» объясняется не лишним хвостом.

## 4. Один следующий шаг

Сверить **смещение тела**, которое использует вендор: в нашем загрузчике тело
начинается с offset **48** (`sizeof(struct wmt_rom_patch)`), а generic-путь
вендора (`mtk_wcn_soc_patch_dwn`, не-multi) отрезает только `sizeof(WMT_PATCH)`
= **28** байт. Если `srh_rom_patch` для ROMv4 отдаёт ядру файл, у которого первые
28 байт — тот же заголовок, то тело у вендора начинается с 28, т.е. включает
`u4PatchAddr/u4PatchType/CRC` (20 лишних байт) — тогда `patchSize` и последний
фрагмент у нас **разные**, и ROM отбрасывает хвост. Проверить по `wmt_launcher`
(`read patch info:0x%02x × 4` — адрес; `patch info × 8` — что именно) и, если
подтвердится, отправлять тело с offset 28 (одна правка — в `t1100_rom_patch_dwn_file`).
