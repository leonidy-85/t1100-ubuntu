# M38 — STP-reinit без power-cycle чип не оживляет; патч стирается сбросом (13.11)

## 1. Прогон ровно по плану (без power-cycle)

Параметры: `t1100_rom_patch=ROMv4_be_patch_1_0_hdr.bin t1100_patch_readback=1
t1100_stp_reinit_after_patch=1`.

```
t1100: reset ack: no
t1100: stp reinit (no cycle) close=0 open=0 mode=0 en=0      <- все rc=0
t1100: hwcode after reinit = 0x00000000 (ret -3)             <- чип НЕ отвечает
t1100: after-reinit patchmem[0x80098020] = 0x00000000 (ret -3)
t1100: after-reinit ctrl GEN_HCR         = 0x00000000 (ret -2)   <- STP уже снят таймаутом
```

Т.е. **STP-reinit без перезапуска домена не помогает**: вызовы `stp_close/open/
mode/en` успешны, но `REG_READ` не обслуживается (`-3`), а следующий таймаут
снимает STP-состояние (`-2`).

## 2. Сравнение с power-cycle (M37)

| | без power-cycle | после power-cycle |
|---|---|---|
| stp close/open/mode/en | 0/0/0/0 | 0/0/0/0 |
| `hwcode` (`GEN_HCR`) | `ret -3` (молчит) | **`0x00000788` (ret 0)** |
| `patchmem[0x80098020]` | `ret -3` | `0x00000000` (ret 0) — **патч стёрт** |

⇒ после доставки патча MCU перестаёт обслуживать STP **навсегда в пределах
питания**; лечится только сбросом домена, который стирает патч. Это значит, что
**сама доставка патча приводит MCU в нерабочее состояние** (вероятно, ROM
начинает исполнять принятый патч и виснет).

## 3. Файлы патча (проверка выбора)

```
1_0: date=20220615154332a ALPS hw=0x008a sw=0x008a addr=0x00098022 type=0x0fe3ffff
1_1: date=20220615154332a ALPS hw=0x008a sw=0x008a addr=0xf0078021 type=0x00000000 (CRC=0)
```

`1_1` адресует `0xf0xxxxxx` (EMI/PDA-пространство) и имеет нулевой тип — это
другой механизм; для ROMv4-адреса `0x98022` подходит `1_0` (наш выбор верен).

## 4. Состояние

`cpupcr` = ROM-значения, `WCIR`/READY = 0, `wlan0` нет; до `WLAN_READY` дело не
доходит (`wlanAdapterStart` падает на `nicpmSetDriverOwn`, как в M32–M35).

## 5. Один следующий шаг

Проверить **хвост тела патча**: у mt6765/mt6761 вендор срезает
`BCNT_PATCH_BUF_CHECKSUM` (2 байта) перед отправкой
(`mtk_wcn_soc_patch_dwn`, ветка `0x6765/0x3967/0x6761`), потому что в файле после
тела лежит контрольная сумма. У `1_0` в заголовке четыре ненулевых `u4CRC`
(байты 32…47), и вполне возможно, что последние 16 байт тела — это тоже CRC,
которую мы отправляем как код: тогда 229 полных фрагментов проходят, а
последний (336 Б, с «мусором» в конце) валит ROM — ровно наблюдаемая картина
(229 ack → молчание). Сверить с `srh_rom_patch`/`wmt_launcher`, вычитать ли для
ROMv4 хвостовую CRC из тела перед `mtk_wcn_soc_normal_patch_dwn()`.
