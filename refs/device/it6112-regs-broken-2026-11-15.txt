Comparison with the working boot state (dmesg "post-dcs" dump at t=2.2 s of
the same boot, refs/device/journal-it6112-resume-2026-11-15.txt.gz):

  - TX 0x00..0x2f, 0x30..0x4f, 0x98..0xd7: identical except two free-running
    counters that change on every dump: TX 0x0e (0x5a, 0x5e, 0x5f, 0x7f seen)
    and TX 0xa6 (0x04, 0x76, 0xcb seen).  TX 0x78..0x97 is a block of such
    counters/status and differs on every read by design.
  - RX 0x00..0x6f: byte for byte identical, including RX 0x21 = 0x08
    (bit3: video format auto-detect done) and the measured timing block.
  - TX 0x05 = 0x00 (HOLD_TX clear), 0x06 = 0x00.

Only the dynamic counters differ, so the chip's register map is intact; the
broken picture is the TX video state machine losing the output timing, not a
lost configuration.

Vendor TX "on" pulse, applied live on this exact state:

  /root/i2cpeek -w 3 0x56 0x05 0xfe
  /root/i2cpeek -w 3 0x56 0x05 0x00

The owner confirmed the picture came back immediately ("Картинка нормальная").
The same pulse had fixed a DPMS off/on breakage on 2026-11-12.
