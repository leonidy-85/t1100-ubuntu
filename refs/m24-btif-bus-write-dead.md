# M24 — окно BTIF не принимает записи (13.11)

Итог рубежа M24: **ROM молчал не «на проводе» — из SoC вообще не уходило ни
байта**. Окно `0x1100c000` write-dead на уровне шины: чтения возвращают
значения (похожие на конфигурацию LK), записи не меняют ни один регистр — ни из
драйвера (`writel`), ни из userspace (`/dev/mem`). Проверено с CONSYS и
выключенным, и включённым (stage=1, `cpupcr=0x1170`).

## 1. Baud/делителя в BTIF нет

`grep -i "baud\|divis"` по вендорскому драйверу
(`drivers/misc/mediatek/btif/common/*`, Hadenix android_kernel_alps-4.4, ветка
`4.4.146`) — **пусто**. В `plat_inc/btif_priv.h` нет регистров делителя; есть
только `BTIF_FAKELCR` (0x0c, «normal mode») и `RTOCNT` (0x54). Блок —
16550-подобный: reset-значения `IIR=0x01`, `LSR=0x60` — это ровно сброс 16550.

Единственная «частота» — CCF-гейт `btifc`:

```c
/* vendor drivers/clk/mediatek/clk-mt6771.c:1173 */
GATE_INFRA0(INFRACFG_AO_BTIF_CG, "infra_btif", "axi_sel", 31),
/* :1059 */ static const struct mtk_gate_regs infra0_cg_regs =
	{ .set_ofs = 0x80, .clr_ofs = 0x84, .sta_ofs = 0x90 };
```

То есть `btifc` = INFRACFG_AO база 0x10001000, set 0x80 / clr 0x84 / sta 0x90,
бит 31, родитель `axi_sel` — совпадает с `CLK_INFRA_BTIF` в mainline
(`include/dt-bindings/clock/mt8183-clk.h:210` = 26, а стоковый DT берёт 27:
нумерация MT6771 = mt8183 + 1, как и для `apdmac` 43 vs `CLK_INFRA_AP_DMA` 42).

Гейт **включён**: `0x10001090 = 0x9beffd5d` (бит31 = 1); проверено и обратное —
CLR бита31 (`0x10001084 ← 0x80000000`) гасит бит в статусе, SET возвращает.
Значит CCF-часть в порядке, дело не в гейте.

## 2. Записи в окно 0x1100c000 не доходят (drugой уровень)

| адрес | что | результат |
|---|---|---|
| 0x1100c068 | `WAT_TIME ← 0x99` | читается `0x12` (как было) |
| 0x1100c054 | `RTOCNT ← 0x77` | читается `0x40` |
| 0x1100c004 | `IER ← 0x1` | читается `0x0` |
| 0x1100c060 | `TRI_LVL ← 0x18` / bit7 loopback | читается `0x5a` |
| 0x1100c000 | 40 записей `THR=0x55` | `LSR` остаётся `0x60` (THRE=1, FIFO не заполнилась) |
| 0x1100c010…0xff0 | запись `0xa5a5xxxx` | читается `0x0` |

Контроль (тот же способ, тот же `/dev/mem`):

* INFRACFG_AO: запись/очистка гейтов **работает** (`0x90` меняется);
* AP-DMA окна BTIF (`0x11000a80`, `0x11000b00`): запись **видна** (`0xa8c` 0→0x2);
* `eem_fsm` (`0x1100b000`): запись **видна** (0→0x8);
* `irtx` (`0x1100d000`): записи **тоже не доходят** (0 остаётся 0).

Т.е. это не «драйвер не пишет» и не «не тот адрес»: два блока периферии
(`btif`, `irtx`) write-dead, остальные — нет.

## 3. Что исключено

* **Часы/гейт** `btifc`: включён (см. §1), `apdmac` (IFR1[18]) тоже.
* **SW-сброс**: банки `0x10001120/0x10001130/0x10001140/0x10001150` = 0
  (`MT8183_INFRACFG_AO_BTIF_SW_RST = 12`, `APDMA_SW_RST = 9`).
* **AXI bus protect** (`0x100012a0`): было `0x18600098` (в т.ч. CONSYS-биты
  13/14), очистили всё (`0x100012a4 ← 0xffffffff` → `0x100012a0 = 0`) —
  записи в BTIF не появились. `PROTECTSTA1` (`0x100012a8 = 0x00380040`) не
  изменился.
* **Состояние домена CONNSYS**: тест повторён при включённом домене
  (`wlan_drv t1100_probe_stage=1`, `cpupcr=0x1170`) — записи так же не проходят.
* **Пейсинг CTS/RTS и wake**: `HANDSHAKE=0`/`BTIF_WAK` не влияют (записи не
  доходят, поэтому и эффекта быть не могло).
* **Пинмукс**: в mainline-драйвере `pinctrl-mt8183` функции BTIF нет вообще
  (`grep -ci btif pinmux-functions` = 0 на живой плате), в стоковом DT у
  `btif@1100c000` нет `pinctrl-*` ⇒ линии не GPIO-мультиплексируемые.

## 4. Следующий шаг (нужен рабочий сток как эталон)

Самый информативный эксперимент — **сравнить состояние AP-инфраструктуры с
рабочим стоком**: загрузить Aurora 5.1.6.110, прочитать те же адреса
(`0x1100c068`, `0x1100c004`, `0x1100c060`) и проверить, принимает ли окно
записи из `/dev/mem` (root есть). Если принимает — снять дамп
`0x10001000-0x10001300`, `0x10003000-0x10003080`, `0x10006000-0x10007000`,
`0x1020e000` (DEVAPC?) до и после и найти различие. Если не принимает и на
стоке — BTIF на этой плате не используется, и транспорт WMT надо искать
в другом месте (MCIF), а не в BTIF.
