# M34 — чтение памяти патча через WMT REG_READ: чип перестаёт отвечать (13.11)

## 1. Как работает REG_READ и с каким адресом

`wmt_core_hw_check()` читает `GEN_HCR = 0x80000008`
(`wmt_core.c`, `wmt_core_reg_rw_raw(0, GEN_HCR, …)`) — **старший бит 31 в адресе
обязателен** (это флаг регистрового пространства CONNSYS). Первый прогон с
адресом `0x00098020` дал `ret -3` именно из-за отсутствия флага; повтор с
`0x80098020` — тоже `ret -3`.

## 2. Результат чтения (прогон с флагом)

```
t1100: ROMv4 patch download -> 0
t1100: reset ack: no
t1100: patchmem[0x80098020] = 0x00000000 (ret -3)
t1100: patchmem[0x80098024] = 0x00000000 (ret -3)
```

`ret -3` — это ветка `Rx REG_EVT fail` в `wmt_core_reg_rw_raw` (после таймаута
там вызывается `wmt_core_trigger_assert()`, `wmt_core.c:650`). Контрольный
`GEN_HCR` в этом прогоне не дошёл (лог обрезан таймаутами по 2 с на слово).

## 3. Сравнение с файлом (таблица)

Тело файла, offset 48 (первые 32 байта, LE-слова) — из `/lib/firmware`:

| смещ. | байты | слово (LE) |
|---|---|---|
| +0 | `44 21 00 00` | `0x00002144` |
| +4 | `a8 00 01 00` | `0x000100a8` |
| +8 | `f4 1e 02 00` | `0x00021ef4` |
| +12 | `18 18 02 00` | `0x00021818` |
| +16 | `b4 2a 03 00` | `0x00032ab4` |
| +20 | `90 50 00 00` | `0x00005090` |
| +24 | `4c 79 02 00` | `0x0002794c` |
| +28 | `48 29 01 00` | `0x00012948` |

Прочитано: **ни одного слова** (чтение не обслуживается, `ret -3`) — сравнение
невозможно, а не «не совпало».

## 4. Почему нельзя утверждать «патч отброшен»

* До патча тот же `REG_READ` работает: `wmt_core_hw_check: get hwcode (chip id)
  (0x788)` — это тот же `wmt_core_reg_rw_raw` с `0x80000008`.
* После загрузки патча REG_READ **не отвечает вообще** (не только по адресу
  патча) — значит чип перестал обслуживать WMT-команды, а не «данных нет».
* Виновник виден в коде: при таймауте `wmt_core_reg_rw_raw` сам вызывает
  `wmt_core_trigger_assert()` (`wmt_core.c:650`) — это отдельный путь, который
  мы **не** заглушали (в M32 глушили только `wmt_lib_trigger_assert` в
  `wmt_ctrl_rx`). То есть первое же чтение с таймаутом усугубляет состояние.

## 5. Что достоверно известно

```
patch download -> 0        (230/230, последний кадр 347 Б ушёл целиком — M33)
reset ack: no
REG_READ после патча: -3 (нет ответа ни по одному адресу)
wlanAdapterStart: nicpmSetDriverOwn (DRIVER OWN, status=0 count=512) → fail,
                  READY=0, wlan0 нет
cpupcr = 0x14f0e (ROM)
```

## 6. Один следующий шаг

Контрольный прогон **без патча** с тем же readback в той же точке
(`t1100_rom_patch` пустой, `t1100_patch_readback=1`): если REG_READ там отвечает
(как `hwcode`), значит именно передача патча переводит ROM в состояние, где он
не обслуживает команды, — и тогда причина в самом процессе загрузки (наиболее
вероятно, что ROM «съедает» последний фрагмент как команду, потому что для
ROMv4 после 229 фрагментов ожидается иная терминация). Если же REG_READ не
отвечает и без патча в этой точке — проблема в порядке инициации (assert-путь),
и его надо глушить целиком.
